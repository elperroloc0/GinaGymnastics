# Архитектурный план проекта: Gina Gymnastics Tracker

## Описание продукта

Система трекинга в реальном времени для вана, который перевозит детей между школой и гимнастическим центром. Проект не отслеживает данные по каждому ребёнку отдельно — фокус на двух ключевых событиях маршрута:

- **Ван прибыл в школу** (точка забора)
- **Ван прибыл в гимнастический центр** (точка доставки)

Плюс live-карта, показывающая текущее положение вана между этими точками. Аудитория — родители (получают уведомления и видят карту) и персонал центра (управляет маршрутами и геозонами).

## Аппаратная часть

- **Трекер:** Teltonika FMM00A — OBD-II plug-and-play, LTE Cat M1, сертифицирован для США (AT&T)
- **GPS-сервер:** Traccar (self-hosted, открытый исходный код) — принимает данные трекера, декодирует протокол (Codec 8), хранит историю координат, детектит вход/выход из геозон нативно

## Разделение ответственности: Traccar vs собственный backend


**Traccar берёт на себя:**
- Приём и декодирование сырого сигнала от трекера
- Хранение истории GPS-точек
- Вычисление геозон (задаются один раз через интерфейс Traccar — координаты + радиус)
- Отправку webhook при событии входа/выхода из геозоны

**Наш backend отвечает за:**
- Всю бизнес-логику: пользователи, роли (родитель/персонал), связь вана с центром
- Приём webhook от Traccar и создание событий в своей базе
- Решение, кого и как уведомить (push/SMS)
- API для фронтенда (история поездок, настройка геозон персоналом)
- Трансляцию live-позиции на фронтенд через WebSocket

Аналогия: Traccar здесь — как Stripe для платежей. Он делает сложную инфраструктурную работу, но не знает ничего о бизнес-логике проекта.

## Структура Django-проекта

Backend строится как несколько приложений Django:

### `fleet`
Статичные данные, которые меняются редко (управляются персоналом вручную через админку):
- `Van` — трекер, IMEI, статус
- `Route` — маршрут школа → гимнастика
- `Geofence` — координаты и радиус точки (школа/зал)

### `tracking`
Ядро проекта — обработка живых данных:
- `ArrivalEvent` — событие входа/выхода из геозоны (timestamp, van, geofence)
- Endpoint приёма webhook от Traccar
- Django Channels consumer для трансляции live-позиции по WebSocket

### `notifications`
Изолированный механизм уведомлений:
- Celery-задачи на отправку push/SMS родителям
- Интеграция с внешним провайдером (Twilio / Firebase)

### `accounts`
Пользователи и роли:
- Модель родителя, модель персонала
- Права доступа: родитель видит только свой маршрут, персонал — больше

**Принцип разделения:** приложения группируются не по "какая таблица", а по тому, кто использует код и как часто он меняется. `fleet` — тихий код, правится персоналом раз в неделю. `tracking` — код, принимающий непрерывный внешний поток данных. Это разные по природе части системы, поэтому они разделены.

## API-слой

**Django REST Framework** поверх всех приложений — единая точка входа для фронтенда: CRUD геозон и маршрутов, история событий, аутентификация.

## Frontend

Отдельный проект (React), не Django templates — общается с backend только через API:

- **HTTP (DRF)** — для истории, настроек, CRUD-операций
- **WebSocket (Django Channels)** — для live-позиции вана
- **Mapbox GL JS** — рендеринг карты и живого маркера

Frontend и backend развёрнуты и разрабатываются независимо (CORS настраивается с самого начала).

## Поток данных целиком

```
Трекер (FMM00A)
    │  сырой GPS-сигнал
    ▼
Traccar
    │  webhook при входе/выходе из геозоны
    │  поток координат для live-карты
    ▼
Django backend (fleet / tracking / notifications / accounts)
    │  DRF API (HTTP)          │  Channels (WebSocket)
    ▼                          ▼
React frontend  ────────────────────────► Mapbox GL JS (live-карта)
```

## Требование автономности

Ключевое требование к готовому продукту: система передаётся компании (Gina Gymnastics) и должна работать **без постоянного ручного участия** — не требуется ежедневный мониторинг или вмешательство в нормальную работу. Техническая поддержка при поломках лежит на разработчике или ИТ-подрядчике компании, но не является частью повседневного цикла.

Это значит, что архитектура должна закладывать не просто работающий MVP, а систему с:

### Автоматическим восстановлением после сбоев
- Все сервисы (Django, Traccar, Celery, Redis, Postgres) запускаются через **Docker Compose** с политикой `restart: unless-stopped` — если процесс упал (например, из-за временной сетевой ошибки), он поднимается сам, без ручного вмешательства
- Celery-задачи на отправку уведомлений должны иметь retry-логику с экспоненциальной задержкой — если Twilio/Firebase временно недоступен, задача не теряется, а повторяется автоматически

### Мониторинга и алертов (не ручной проверки)
- Простой health-check endpoint (`/health/`) для каждого сервиса
- Автоматический алерт разработчику/ИТ (email или Slack webhook), если:
  - Трекер не присылал координаты дольше N минут в рабочее время (обрыв связи/села батарея)
  - Django или Traccar недоступны
  - Очередь Celery накопила необработанные задачи
- Без алертов "автономность" превращается в риск: система тихо перестаёт работать, а никто не узнаёт, пока не пожалуется родитель

### Устойчивости к внешним сбоям
- Что происходит, если Traccar временно потерял связь с трекером — очередь webhook-данных не должна теряться
- Что происходит при перезапуске сервера — миграции и стартовые данные (геозоны, маршруты) должны подниматься автоматически, не вручную через shell

### Обновлений без даунтайма (или с минимальным)
- Хотя бы базовый CI/CD (например, GitHub Actions), чтобы будущие правки (например, ИТ компании захочет изменить радиус геозоны через админку — это не требует деплоя, но если понадобится код-фикс) не требовали ручного захода на сервер и ручных команд

## Хостинг

Ещё не выбран — стоит закладывать в архитектуру заранее, так как от этого зависит, как настраивается автозапуск и мониторинг. Разумные варианты для проекта такого масштаба (один клиент, невысокая нагрузка):

- **Railway** или **Render** — простой деплой из Git, встроенный restart при падении, минимальная ручная настройка DevOps. Хорошо подходит, если хочется меньше возни с серверной инфраструктурой
- **VPS (DigitalOcean/Hetzner) + Docker Compose** — больше контроля, дешевле при росте нагрузки, но требует самостоятельно настроить restart-политики и мониторинг (ничего не идёт "из коробки")

Для требования автономности первый вариант снижает риск, что что-то сломается на уровне инфраструктуры, которую некому чинить.

## Роли пользователей и права доступа

Система разделена на четыре уровня, но важно различать, какие из них — роли внутри приложения, а какие — доступ к инфраструктуре.

### Три роли внутри Django (`accounts`)

**Родитель** — самые узкие права. Видит только своего ребёнка/ван, получает уведомления о прибытии. Не имеет доступа к данным других семей.

**Оператор** — вносит и редактирует операционные данные: родителей, детей, школы, маршруты, геозоны. Не может создавать других операторов и не имеет доступа к системным настройкам.

**Админ (суперюзер)** — управляет операторами (создание/удаление аккаунтов, назначение прав) и общими настройками системы. Для этого уровня в большинстве случаев достаточно встроенного **Django admin** — он из коробки даёт интерфейс для управления пользователями и правами, отдельный кастомный UI для этой роли обычно не требуется.

Реализация — через кастомное поле `role` на модели пользователя (`accounts.User`) в сочетании с DRF `permission_class`, которые фильтруют доступные данные по роли и по `request.user`. Родитель и оператор используют один и тот же API, но с разными правами на чтение/запись — это не разные эндпоинты, а разная логика прав внутри одних и тех же вьюх.

### ИТ — доступ к инфраструктуре, а не роль в приложении

ИТ-специалист, обслуживающий систему после передачи (проверка логов, устранение сбоев), не логинится как пользователь Django-приложения — эта роль вне модели ролей выше. Ему нужен:

- Доступ к логам контейнеров (`docker logs`, либо внешний сервис вроде Sentry/Grafana, если будет подключён)
- Доступ к health-check эндпоинтам (см. раздел "Требование автономности")
- SSH/панель управления хостингом

Отдельный логин в самом приложении для этой роли не создаётся, чтобы не смешивать инфраструктурный доступ с бизнес-логикой прав внутри `accounts`.

## Эксплуатационные аспекты

Раздел покрывает то, что не входит в основную архитектуру, но критично именно потому, что система передаётся компании и должна работать без постоянного участия разработчика.

### Аутентификация и управление доступом

Не только "кто что видит" (это уже описано в разделе про роли), но и сам механизм входа:

- Выбор между JWT и session-based аутентификацией в DRF (JWT обычно удобнее для связки с отдельным React-фронтендом)
- Как родитель получает первый доступ — вероятнее всего, оператор создаёт аккаунт при регистрации ребёнка и высылает приглашение (email/SMS со ссылкой на установку пароля), а не родитель регистрируется сам
- Восстановление доступа: что происходит, если родитель потерял телефон/забыл пароль — нужен стандартный flow сброса пароля, не требующий участия разработчика
- Политика паролей и, если потребуется, возможность 2FA для операторов/админа (более высокий риск при компрометации аккаунта с CRUD-правами)

### Резервное копирование

Критично для требования автономности — если сервер или диск выйдут из строя, история событий и аккаунты не должны теряться:

- Автоматический ежедневный дамп PostgreSQL, с выгрузкой во внешнее хранилище (S3, Backblaze B2 или встроенный бэкап хостинга, если Railway/Render его предоставляют)
- Хранение бэкапов за последние N дней (ротация, чтобы не копить бесконечно)
- Периодическая проверка, что бэкап реально восстанавливается — бэкап, который никто не проверял, не даёт гарантий

### Замена и обслуживание трекера

Процесс на случай, если устройство сломается, потеряется или его нужно заменить (новый ван, ремонт):

- У оператора должна быть простая возможность привязать новый IMEI к существующему `Van` через интерфейс — без обращения к разработчику
- Короткая инструкция (для персонала центра) о физической переустановке OBD-трекера в другой ван

### Безопасность webhook-эндпоинта

Endpoint, принимающий события от Traccar, не должен быть открытым для кого угодно, кто узнает URL:

- Аутентификация запроса через shared secret / токен в заголовке, проверяемый на стороне Django перед обработкой
- Ограничение по IP, если Traccar размещён на известном статическом адресе (дополнительный, но не обязательный уровень защиты)
- Без этого посторонний может слать поддельные события о прибытии, вызывая ложные уведомления родителям

### Стоимость и лимиты внешних сервисов

- Аккаунт Twilio/Firebase для уведомлений — оплата и лимиты сообщений не бесконечны. Нужно решить заранее, на чьё имя оформлен аккаунт и кто отслеживает баланс
- Стоит настроить алерт при приближении к лимиту или исчерпании баланса — иначе уведомления родителям молча перестанут доходить

### Часовые пояса и рабочие часы

Алерт "трекер не присылал координаты дольше N минут" должен учитывать расписание маршрута — иначе ночью или в выходные будут ложные срабатывания, когда ван просто не должен ехать.

### Тестовое покрытие

Хотя бы базовые автотесты для критичных участков — обработки webhook, прав доступа по ролям, отправки уведомлений — снижают риск, что будущее вмешательство (правка кода со стороны ИТ-подрядчика компании) сломает что-то незаметно, без немедленной обратной связи.

Без этой документации "автономность" на практике зависит от памяти разработчика, а не от системы.



- Проверка структуры моделей (`ForeignKey`, связи между `fleet` и `tracking`) до написания миграций
- Настройка Django Channels — правильная организация `consumers.py` и `routing.py`
- Организация Celery-задач в `notifications` — паттерны retry-логики при недоступности внешнего провайдера

- Простой, но надёжный подход к алертам (email/Slack) при сбоях, реализуемый в рамках учебного проекта без сложной DevOps-инфраструктуры
- Правильный подход к аутентификации (JWT vs sessions) при разделении Django backend и React frontend
- Настройка автоматического бэкапа PostgreSQL и проверка его восстанавливаемости
